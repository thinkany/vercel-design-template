# Rich text editor for posts and richtext fields (TipTap, markdown on disk)

**Status:** spec'd 2026-09-02, agreed (Rob: "designers can't be expected to know markdown").
**Sequence:** after the media picker (Phase 2 item 3), since image insertion is the picker.
**Estimate:** two to three days.

## Goal

A standard WYSIWYG editor wherever a designer writes prose in the CMS: the post body
today, the `richtext` fields of content types, and later a block prop or two. The
designer types in a rendered document; the file on disk stays **markdown**, so posts and
entries remain portable, diffable, and rendered by Astro exactly as now.

## Why TipTap

ProseMirror underneath (the editor model every serious editor uses), a markdown
serializer/parser that round-trips the subset markdown can express, and custom nodes
later (embedding a block or a reference inside a post) that a markdown-native editor
(EasyMDE, Toast UI) could never grow into. One editor for every rich field.

## Packages (pinned at spec time)

| package | version | role |
|---|---|---|
| `@tiptap/core` | 3.31.0 | editor |
| `@tiptap/starter-kit` | 3.31.0 | paragraphs, headings, bold/italic/strike, lists, blockquote, code, hr, history |
| `@tiptap/extension-link` | 3.31.0 | links |
| `@tiptap/extension-image` | 3.31.0 | images |
| `tiptap-markdown` | 0.9.0 | markdown in/out (peer: `@tiptap/core ^3`) |

App dependencies (root `package.json`), never the scaffold's: the editor lives in the app.

## Bundling

`shell.js` is a classic script with no bundler, and TipTap is ESM-only. A build step
`desktop/build/bundle-editor.cjs` (esbuild, already a dependency) bundles the packages
above into one IIFE, `desktop/vendor/editor.js`, exposing `window.TAEditor = { create }`.
Committed output (so `npm run desktop` needs no step) and regenerated by `predist`.
`strip-comments` skips `desktop/vendor/**` (third-party, already minified).

## Mount points

`TAEditor.create(host, { markdown, onChange, onPickImage })` returns
`{ getMarkdown(), setMarkdown(md), destroy() }`.

- **Post body** (`renderSitePost`): replaces the textarea. The draft's `body` is read
  through `getMarkdown()` on save.
- **richtext fields** (`siteTypeFieldControl`, kind `richtext`): same, per field.
- Anything else stays a plain input.

## Toolbar (markdown's subset, deliberately)

Paragraph / H2 / H3 · bold · italic · strike · bullet list · numbered list · quote ·
code · link · image · horizontal rule · undo / redo. No H1 (the title is the H1), no
colors, no font sizes, no alignment: markdown can't carry them, and a post shouldn't.

## Markdown mapping

`tiptap-markdown` with `html: false` (no raw HTML in files), `bulletListMarker: "-"`,
`breaks: false`. Images serialize as `![alt](/images/x.jpg)`; links as `[text](href)`.
Round-trip rule: what the toolbar can't express can't get into the document, so what's
saved always re-opens identically.

## Images

The image button opens the **media picker** (Phase 2 item 3): browse `public/images`,
upload into it, pick one → `![alt](/images/name.jpg)`. Alt text is asked for on insert
(a one-field prompt), since it's the accessibility requirement the design side already
enforces. No base64, no external URLs pasted silently (a pasted URL becomes a link).

## Fallback

A "Markdown" toggle under the editor shows the textarea with the raw markdown, for the
rare fix the toolbar can't make (and for trust: the designer can always see the file).

## Not in scope

Collaborative editing, comments, version history (git is the history), embedding blocks
inside a post (a later custom node), tables (markdown tables exist; add when asked).

## Phases

1. `bundle-editor.cjs` + `desktop/vendor/editor.js` + `TAEditor.create` with StarterKit,
   Link, Image, Markdown; mount on the post body with the toolbar and the Markdown
   toggle. Verify: open the sample post, edit, save, Astro renders it; the raw file is
   clean markdown.
2. richtext fields in content types.
3. Image button → media picker (once it exists), alt prompt.
4. Polish: keyboard shortcuts list in the help drawer; paste handling (plain text keeps
   line breaks as paragraphs, HTML paste is converted through the parser).
